# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> Written for the state of `main` with WEAVE merged. If a path or an id here does not exist, the doc is wrong and worth fixing — there is no branch left in flight for it to be ahead of.

## What this is

**Loom** — a browser-based, session-based music workstation built on Web Audio + TypeScript + Vite. It grew out of a Roland TB-303 bass synth + drum machine and still has those at its core, but is now a multi-engine instrument host: **6 melodic engines (TB-303, Subtractive, FM, Wavetable, Karplus, Westcoast) + a Sampler + an Audio-channel engine + a Drum machine** (9 registered engines), arranged as **lanes** that play **clips** in **scenes**, with per-lane modulation, inserts/FX, a mixer with sidechain compression, MIDI import, and global undo. **Synthesis runs in an AudioWorklet** (`src/audio-worklet/` + the pure DSP kernel in `src/audio-dsp/`); the mixer, inserts and master stay native Web Audio nodes. Audio is loaded into IndexedDB by the Sampler, the Audio channel, the sample-based drum kits, and the Stems importer.

**The interesting half of Loom is no longer in `src/`.** All six melodic engines and all fifteen FX inserts are **external drop-in plugins**: a self-contained directory under [plugins/](plugins/), compiled by its own CLI into `public/plugins/<id>/`, and loaded by the browser **at runtime** off a JSON manifest. They compile against the published SDK, [packages/loom-plugin-sdk/](packages/loom-plugin-sdk/) (`@loom/plugin-sdk`), and reach the host through a small runtime ABI (`globalThis.Loom`) — never through an import of this repo's source. What is left in-tree is the **host**: the three engines that own browser resources (`sampler`, `audio`, `drums-machine`), the LFO/ADSR modulators, the note-FX, and everything that arranges, schedules, mixes and saves.

Two consequences worth internalising before you touch anything:

- **`plugins/` is source; `public/plugins/` is build output.** Editing a plugin and running only `vite build` ships the OLD plugin. `npm run build` runs `build:plugins` first for exactly this reason.
- **The core may not know a plugin's name.** Anything the core needs to ask about a component goes through the one door, [src/plugins/capabilities.ts](src/plugins/capabilities.ts). An `engineId === '…'` comparison anywhere else is a bug.

## Commands

- `npm install` — install dependencies
- `npm run dev` — start Vite dev server (hot reload) at <http://localhost:5173>
- `npm run build` — build every plugin, then typecheck (`tsc`) + bundle to `dist/`
- `npm run build:plugins` — compile `plugins/*` into `public/plugins/` and rewrite `public/plugins/index.json`. Runs as the first step of `build`; run it alone when you touched only a plugin.
- `npm run plugin -- new plugins/<id> [--js]` / `npm run plugin -- build plugins/<id>` — scaffold or build a single plugin ([tools/loom-plugin/cli.mjs](tools/loom-plugin/cli.mjs)).
- `npm run preview` — serve the production build locally
- `npx tsc --noEmit` — typecheck without bundling
- `npm test` — full suite: Vitest unit tests + Playwright e2e tests, colour-free (`NO_COLOR=1` via `cross-env`)
- `npm run test:unit` — Vitest only (no browser)
- `npm run test:fast` — everything except DSP renders (inner-loop TDD), colour-free
- `npm run test:dsp` — only the real-DSP renders (slower, requires `node-web-audio-api`), colour-free
- `npm run test:e2e` — Playwright tests in `tests/e2e/` against `vite preview` on port 4173
- `npm run test:e2e:headed` — same but with a visible browser window for debugging
- `npm run test:wav-diff` — compares `test/output/*.wav` (last run) against `test/golden/*.wav` (committed reference) and prints peak/RMS/L2 deltas. Never fails CI — human inspection tool.
- `npm run test:wav-bless` — overwrites `test/golden/` with the current `test/output/`. Deliberate action; commit the result.
- `npm run build:pages` — the GitHub-Pages build (`--base=/Loom/`); what the deploy actually ships.
- `npm run build:manual` — regenerate `docs/manual/` (+ `manual:shots`, `manual:pdf`).
- `npm run test:watch` — Vitest in watch mode.
- `npm run bump` — manual version bump (versioning is never automatic).

**Test colour convention:** every npm test script is wired with `cross-env NO_COLOR=1` so terminal output stays grayscale. When invoking vitest directly (e.g., a single file), prefer `NO_COLOR=1 npx vitest run path/to/file.test.ts`. Do NOT add `--reporter=...` to override — the npm scripts already do the right thing.

No linter is configured.

## Gotchas (read before running tests / shipping)

- **`test:e2e` / `npm test` serve `dist/` with NO build step.** Playwright boots `vite preview`, which serves the last production build. If you changed `src/` and didn't `npm run build`, the e2e suite tests a **stale bundle** — the newest features fail with "element not found" and it looks like a regression. Always `npm run build` before `npm run test:e2e`.
- **A stale `public/plugins/` looks exactly like a broken engine.** The dev server does not compile `plugins/` — it serves whatever `build:plugins` last wrote. Change `plugins/fm/dsp.ts`, reload, and you hear the previous version with no warning; forget to build a NEW plugin and its engine is simply absent from the selector. `npm run build:plugins` after every plugin edit.
- **A plugin that throws is skipped, not fatal.** [src/plugin-host/plugin-host.ts](src/plugin-host/plugin-host.ts) validates each manifest as DATA before a line of it runs and **rolls back** anything a half-loaded plugin already registered. So a broken plugin shows up as one missing engine plus an entry in the load report — never a blank app, and never a half-registered engine that is visible in the selector and silent at note time. Read the report before concluding the host is at fault.
- **`test:unit` has a flaky teardown.** It occasionally exits non-zero with `ERR_IPC_CHANNEL_CLOSED` (tinypool / `node-web-audio-api` worker shutdown) **after all tests pass**. Vitest is configured to run files serially because `node-web-audio-api` is unsafe under parallel forks; the teardown error is not a test failure — re-run to confirm green.
- **Live param tweaks reach the note already sounding** — continuous engine params are read every sample from the lane's smoothed bag (`ParamSmoother` in `VoiceManager`). STRUCTURAL params still apply to the next trigger only: waveform, filter model, unison size, and every envelope TIME (our envelopes are closed-form over elapsed time, so re-reading an attack mid-note would step the amplitude). Drums is out of scope.

## Testing layout

Four layers, distinct technique per risk class:

1. **Pure** — schemas, scales, migrations, pattern/session/arrangement logic, modulation math. `src/**/*.test.ts` (not `.dsp` or `.wiring`).
2. **Scheduling (mocks)** — the per-lane look-ahead scheduler and session runtime via a fake clock. [src/core/lane-scheduler.test.ts](src/core/lane-scheduler.test.ts) and [src/session/session-runtime.test.ts](src/session/session-runtime.test.ts).
3. **DSP real** — audio actually rendered and measured, in two techniques. The **pure kernel** is driven sample by sample with no `AudioContext` (`audio-dsp/drums/new-voices.dsp.test.ts`, `audio-dsp/modulation-scope.dsp.test.ts`); the **Web Audio nodes that stayed native** render through `OfflineAudioContext` (via [node-web-audio-api](https://github.com/ircam-ismm/node-web-audio-api), globalized in [test/setup.ts](test/setup.ts)). Files end in `.dsp.test.ts` — glob for them rather than trusting a list. **A plugin's DSP is tested inside the plugin**, next to the code (`plugins/<id>/dsp.test.ts`, and `plugins/tb303/tb303-parity.dsp.test.ts` which pins the 303 against a committed `reference-render.json`); `packages/loom-plugin-sdk/src/sdk-parity.test.ts` guards the SDK primitives those plugins share. **There is no per-engine WAV battery any more:** `runStandardEngineBattery` in [test/dsp-battery.ts](test/dsp-battery.ts) survives with **zero callers**, so nothing writes `test/output/` and `test:wav-diff`/`test:wav-bless` only print "does not exist"; the 90 WAVs in `test/golden/` are orphans of the batteries the worklet cutover removed. Reviving that loop is a decision, not a step.
4. **Modulation (objective, end-to-end)** — renders each engine through the REAL in-engine path (`ModulationRuntime` → `VoiceManager` → renderer) with an LFO/ADSR on a continuous param and measures that the rendered sound changes (+ a negative control). [src/audio-dsp/modulation-pipeline.test.ts](src/audio-dsp/modulation-pipeline.test.ts) — it recovered the per-engine modulation coverage the worklet rewrite dropped (the old `.wiring.test.ts` routed LFO/ADSR into a Web-Audio `AudioParam`, which no longer matches how the worklet engines modulate). One `.wiring.test.ts` remains — `core/ducker-subgraph` — still covering Web-Audio subgraph wiring like sidechain.

Assertion rule: **always relative**. Use ratios (`>`, `<`, `> * 2`), never absolute magnitudes. Absolute thresholds are a brittleness smell; if you write one, justify it in a comment.

## Architecture

**Three trees, one contract.** `src/` is the HOST — scheduling, session model, mixer, UI, save. `plugins/` holds the COMPONENTS that make sound. `packages/loom-plugin-sdk/` is the contract between them, and it is deliberately narrow: the runtime ABI (`globalThis.Loom`) carries no DSP at all, so everything a plugin uses is compiled into the plugin's own bundle and the ABI can stay stable across versions.

The host's spine: a **registry of engine/fx/modulator components**, a **`SessionState`** data model (lanes → clips → scenes), and a **`LaneResourceMap`** that owns the live audio nodes for each lane.

### The plugin side

- **[plugins/](plugins/)** — 23 shipped plugins, each a directory with a `plugin.json` manifest plus its code: **6 engines** (`tb303`, `subtractive`, `fm`, `wavetable`, `karplus`, `westcoast`), **15 inserts** (`autowah`, `bitcrusher`, `chorus`, `compressor`, `delay`, `distortion`, `flanger`, `gate`, `limiter`, `multifilter`, `phaser`, `reverb`, `ringmod`, `tremolo`, `width`), **1 modulator** (`sh`, sample & hold) and **1 panel** (`weave` — a whole VIEW, see below). A component that synthesises ships `dsp.ts` → `dsp.js`, loaded into the AudioWorklet; an insert ships `main.ts`, which builds native Web Audio nodes on the main thread; a panel ships `main.ts` too and is handed a DOM root and a `PanelContext`. The manifest is the whole declaration: params, group table, shipped modulators, `presets.json`, and the `capabilities` block the host reads. `plugins/audio-probe/` is `private: true` — a fixture for the host's own tests, never built into `public/plugins/`.
- **[packages/loom-plugin-sdk/](packages/loom-plugin-sdk/)** — `@loom/plugin-sdk`: manifest + param types, and the DSP primitives worth sharing (`osc`, `sync-osc`, `ladder`, `filter`, `filter-stack`, `unison`, `fold`, `comb`, `adsr`, `mod-env-host`, `reverb-ir`). What earns a place here is fitting in ANY engine, not being used by two of ours — what stays inside a plugin is what *is* that engine's identity (its wave tables, its accent curve). **One line in [index.ts](packages/loom-plugin-sdk/src/index.ts) divides two species:** everything above it runs per-sample inside the worklet with no `AudioContext`; `modulated-delay`, `signal-max` and `envelope-follower` below it BUILD NATIVE NODES and only run on the main thread. Importing one into the other's realm does not work.
- **[src/plugin-host/](src/plugin-host/)** — how a plugin gets in. The browser cannot list a directory, so `public/plugins/index.json` **is** the discovery mechanism. [plugin-host.ts](src/plugin-host/plugin-host.ts) fetches each manifest, validates it as DATA before a line of it runs ([manifest-validate.ts](src/plugin-host/manifest-validate.ts)), adopts its components, seeds its presets, and **fully rolls back** a plugin that throws — including one whose components were already adopted before its own module blew up. [loom-api.ts](src/plugin-host/loom-api.ts) installs the main-thread half of `globalThis.Loom` and turns manifest components into registered engines/modulators/fx factories; the worklet half is installed by `loom-processor.ts`. [module-loader.ts](src/plugin-host/module-loader.ts) fetches a plugin's JS and evaluates it through a **`blob:` URL** — a bare `import(url)` works in the build but breaks under `npm run dev`, because Vite refuses to serve a file in `public/` as a module. The blob path behaves identically in both modes and is the same mechanism a user-installed plugin will need when its bytes live in IndexedDB.

### The host

- **[src/core/](src/core/)** — shared DSP primitives and pure logic. `drums.ts` (the `KITS` parameter bags + `DRUM_LANES`/`seedSynthState`/`chokeGroupMates` — pure data since the `DrumMachine` class was deleted; the DSP is `audio-dsp/drums/voices.ts`), `sequencer.ts` (the master clock + `sessionTick`; `onLookahead` lives in `app/performance-feature.ts`), `lane-scheduler.ts` (`tickLane` note-based look-ahead), `lane-resources.ts` (`LaneResourceMap`: per-lane strip + engine + insert chain), `mixer.ts` (`buildMixerColumn`) + `master-strip.ts` + `master-bus-strip.ts`, `insert-chain.ts`, `fx.ts` (`ChannelStrip`, `MasterCompressor`, EQ params), `comp-block.ts` (`CompBlock`), `send-bus.ts`, `sidechain-bus.ts` + `ducker-subgraph.ts`, `history.ts` (undo/redo controller), `knob.ts` + `select-control.ts` (automatable UI controls), `clip-axis.ts` (the single owner of a clip's zoom/scroll — followers MEASURE the primary viewport, they do not recompute it), `pianoroll.ts` (+ zoom/range/templates), `scene-ring.ts` + `scene-countdown.ts` (the launch-countdown sector), `meter.ts` (time signature), `tempo-map.ts`, `notes.ts`, `velocity-gain.ts`, `comp-state.ts`, `transport-state.ts`.
- **[src/engines/](src/engines/)** — the host side of an instrument: the `SynthEngine` abstraction ([engine-types.ts](src/engines/engine-types.ts)) + [registry.ts](src/engines/registry.ts). Only **three** engines still have a file here — `sampler`, `audio` (dedicated audio channel) and `drums-engine` — because each owns browser resources (decoded buffers, IndexedDB, per-voice `AudioParam`s) that an external plugin has no way to hold. They register a **data-only descriptor** ([descriptor-engine.ts](src/engines/descriptor-engine.ts)) whose synthesis methods are inert; the six melodic engines register the *same* descriptor shape from their manifest instead, through `loom-api`. Params are `EngineParamSpec[]` ([engine-params.ts](src/engines/engine-params.ts)) turned into controls by one builder, [engine-param-grid.ts](src/engines/engine-param-grid.ts), whose row/section layout comes from that engine's group table ([engine-param-groups.ts](src/engines/engine-param-groups.ts) in-tree, or `groups` in the manifest). Also here: the lane engine wrappers (`worklet-lane-engine`, `sampler-worklet-engine`, `drums-worklet-engine`, `audio-worklet-engine`) and the selector ([engine-selector-ui.ts](src/engines/engine-selector-ui.ts)). Worklet-hosted engines modulate INSIDE the worklet, so their `getAudioParams()` returns an empty map on purpose; only Drums and Sampler hand out real `AudioParam`s for the Web-Audio binder.
- **[src/session/](src/session/)** — the session model and its UI. [session.ts](src/session/session.ts) (the clip/lane/scene factories, re-exporting the data shapes from `session-types.ts` and the move/copy/duplicate/delete ops from `session-ops.ts`; clips hold a unified `notes: NoteEvent[]`), [session-runtime.ts](src/session/session-runtime.ts) (launch/scene/quantize/`tickSession`), `session-host.ts` (the UI controller that owns lanes — and the **single door for lane selection**, see below), `session-ui.ts` (clip grid + drag), `session-inspector.ts`, `clip-editors/` (router → `piano-roll` or `drum-grid`), `session-engine-state.ts` (mirrors knob/modulator/sampler-keymap edits into `lane.engineState`), `session-migration.ts` (load-time normaliser).
- **[src/modulation/](src/modulation/)** — `ModulationHost`, `ModulatorScope` (shared vs per-voice), `modulator-registry.ts` (the door BOTH an in-tree modulator and a plugin one come through), and the connection binder that routes a modulator into a target `AudioParam` by id.
- **[src/plugins/](src/plugins/)** — what is left of the in-tree SPI, now a small surface. [capabilities.ts](src/plugins/capabilities.ts) is the ONE door through which the core asks what a component can do (`clipContent`, `slide`, `outputTrim`, `acceptsNoteFx`, …) — built-ins answer from code, plugins from their manifest, and the caller cannot tell which. Plus `registry.ts`/`types.ts`, `modulators/` (`lfo`, `adsr` — they call `registerModulator` at module scope, not through the glob's shape check) and `notefx/` (`arp`, `chord`, `random` — three per-lane note-FX factories that call `registerPlugin` at module scope, since `kind: 'notefx'` falls outside the shape check; their chain and UI live in `src/notefx/`). **There is no `fx/` directory here any more** — every insert is an external plugin. `plugin-bootstrap`'s eager `import.meta.glob` over `src/engines/*` + `src/plugins/**` now exists mostly to RUN those module-scope registrations and to bridge engine descriptors into the plugin registry.
- **[src/presets/](src/presets/)** — presets are **JSON assets**, loaded/validated by `preset-loader.ts` and applied via `preset-apply.ts`. A melodic engine's presets ship **with the plugin** (`plugins/<id>/presets.json`, seeded by `plugin-host` at load); `public/presets/` now holds only what the in-tree engines need — `sampler.json`, `drums-machine.json` and `drum-kits.json` (77 sample kits + 13 synth). A preset may carry its own `modulators` (an LFO/ADSR shipped with the sound).

  **A bundled SAMPLER instrument is registered somewhere else**: `public/instruments/<id>.json` plus a line in `public/instruments/index.json`, keyed by `family` — `melodic` or `loop`. It is NOT a `sampler.json` preset, and the two are not interchangeable: a preset carries its zones inline, an instrument is fetched by id. The dropdown groups them separately (Presets / Drumkit / Instrument / Loop), and a sampler lane records which one it plays in `engineState.sampler` (`presetName` / `drumkitId` / `instrumentId`, mutually exclusive) rather than in `enginePresetName` — so its dropdown selection is DERIVED from the lane, not from what someone last picked.
- **[src/midi/](src/midi/)** — pure SMF parser (`midi-parse.ts`) → `midi-to-session.ts` transform, GM matching (`gm-lookup.ts`), plus the import UI + audition.
- **[src/samples/](src/samples/)** — sample types, IndexedDB store + decoded-buffer cache, keymap resolution + repitch, import metadata.
- **[src/performance/](src/performance/)** — the arrangement/record model: `rec-state`, `arrangement-ops`, `arrangement-runtime` (record clip-launches + knob automation, replay them). Takes now surface as timeline bands (`performance-ui.ts` `renderPerformanceView`) and persist in v3 saves (`SavedStateV3.arrangement`).
- **[src/instrument-presets/](src/instrument-presets/)** — the preset surface, in four files that each do one thing. [instrument-preset-select.ts](src/instrument-presets/instrument-preset-select.ts) owns `#instrument-preset-select`, the ONE dropdown every non-drum lane uses, and the Load / Save As… / Delete beside it; [drums-preset-select.ts](src/instrument-presets/drums-preset-select.ts) owns the drums page's kit picker, which is a different thing; [preset-select-state.ts](src/instrument-presets/preset-select-state.ts) holds what both write (the deps, which preset each lane has, which lane each select shows); [user-preset-store.ts](src/instrument-presets/user-preset-store.ts) is the user presets, **keyed by engine id** under `loom-user-presets-v1`. `snapshotEngineParams` walks the params the engine DECLARES — never a hardcoded list — and skips the strip params, because level/pan/sends/EQ are the desk and not the patch. The remaining `poly-*` files are Subtractive's own preset data (`poly-params`, `poly-preset-store`, `poly-preset-apply`, `poly-preset-templates`); the directory was renamed from `src/polysynth/` and those files were not.
- **"poly" vs "instrument" — never sweep-rename "poly".** The page that paints the controls of every non-drum lane is `data-page="instrument"` (it was `poly`, after the `PolySynth` class the worklet cutover deleted — no engine implements `getPolySynth()`/`setPolySynth()` and nothing constructs one). `LaneEngineHostState.instrumentPageLaneId` is the lane painted on it — deliberately NOT the selected lane, since a drum lane routes to the drums page instead. Three `poly` names survive on purpose, each for a reason that costs something real to break:
  - **`polyBlep`** — oscillator anti-aliasing, in the SDK DSP. Renaming it corrupts the sound.
  - **`polyphony`** — a plugin-manifest field, validated by `manifest-validate.ts`.
  - the **`poly` param-group id and the `poly.voices` param id**, carried by five plugin manifests (fm, karplus, subtractive, wavetable, westcoast). Both are plugin ABI, and `poly.voices` is a saved param id besides.

  `POLY_PRESETS_KEY = 'tb303-poly-presets-v1'` used to head that list. It is gone: no released build ever wrote it, so when the per-engine store replaced it there was nothing to migrate and no reason to keep a reader for it.
- **[src/app/](src/app/)** — what used to be `main.ts`'s boot glue, one closed loop per file (~37 modules). The audio spine: `audio-graph` (sum bus → `MasterBusStrip` → master insert chain → `MasterShaper` → `MasterCompressor` → soft-clip → analyser, plus the `FxBus` sends and the `SidechainBus`), `lane-allocator` (`ensureLaneResource`/`swapLaneEngine` — the sole allocation path — and `WORKLET_ENGINE_IDS`, which is no longer a hand-maintained literal but a live view over "is this id worklet-hosted", true for any plugin id), `trigger-dispatch`, `live-voice-registry`, `mute-solo`, `bpm-broadcast`, `track-ids`. The features `main.ts` now merely calls at boot: `transport-controls` (BPM/swing/volume/meter), `menu-wiring` over `menu-actions`/`menu-spec`/`menu-bar`/`menu-shortcuts`, `session-lifecycle` (the three routes that replace the whole session), `save-history-wiring` (SaveManager + undo as one object graph), `midi-import-wiring` + `import-lane-prep`, `midi-control-wiring` (the live MIDI surface), `recording-feature` (REC and its three take modes), `stems-feature`, `engine-selector-wiring`, `engine-swap`, `knob-mounting` + `knob-menu-wiring` + `knob-registry-prune`, `automation-recording` + `automation-writes`, `xy-panel-wiring`, `performance-feature` + `arrangement-playback`, `plugin-bootstrap`, `lane-host-wiring`. If you are looking for the code behind a control it is almost never in `main.ts` — find the `wireX` call that mentions it and open that module.
- **Autosave is OPT-IN and off by default**, and until 2026-08-08 it did not exist at all: the recovery copy was only ever written as a side effect of a MANUAL save (`saveNamedEntry` writes the named entry and the copy from one object), and `sessionHost.deps.saveSession` is assigned by nobody — every `saveSession?.()` in the tree is a no-op. `save/autosave.ts` now debounces and writes the recovery slot ALONE (an autosave that also made a named entry would fill the save list); `save/app-prefs.ts` holds the flag in localStorage, never in a save file, because a project travels and loading someone else's session must not change your machine. It fires off `autoHistory.onChange` — already deduped and gesture-aware — PLUS an explicit nudge from `onWeaveChanged`, since the weave is deliberately not an undo entry and nothing else would ever report that it moved.
- **[src/save/](src/save/)** — `SaveManager` persists **session-only** state as `schemaVersion: 3` (`saved-state-v3.ts`); `history-wiring.ts` (`withUndo`/`attachKnobUndo`/keyboard) bolts undo onto every mutation site.
- **[src/main.ts](src/main.ts)** — boot + remaining DOM glue: builds the UI, allocates lanes, wires controls, resumes the `AudioContext` on first play.
- **[src/audio-dsp/](src/audio-dsp/)** — the pure DSP kernel the worklet runs, minus the engines. `voice-manager.ts`, `scheduler-queue.ts`, `modulation-runtime.ts` + `modulator-kernels.ts`, `renderer-registry.ts` (**now populated at runtime by plugins**, not by in-tree imports — there is no `*-renderer.ts` per melodic engine any more), `param-index.ts` + `param-smoother.ts` (params are addressed BY INDEX in the audio loop — zero name lookups per sample), `gain-staging.ts`, and the DSP that stayed in-house: `drums/` and `sample/`. Plain JS/TS — unit-testable with no AudioContext.
- **[src/audio-worklet/](src/audio-worklet/)** — the processors + their typed node wrappers: `loom-processor`/`loom-node` (melodic), `drums-*`, `sampler-*`. Processors are referenced ONLY via `?worker&url` and their registered string name — never imported on the main thread (see `processor-name.ts`). `loom-processor.ts` installs the worklet half of `globalThis.Loom` (`registerRenderer`, `registerModulatorKernel`) **before** any plugin `dsp.js` is `addModule`'d; that global is the only way a separately-added plugin module can reach this bundle's registry.
- **[src/export/](src/export/)** — offline scene/WAV render + live take recorder. It must replicate the LIVE path (presets, automation, worklet registration) or exports drift from what you hear.
- **[src/control/](src/control/)** — live-MIDI control surfaces (APC Key 25 profiles, `loom-facade`) + computer-keyboard-as-MIDI + live note recording.
- **[src/stems/](src/stems/)** — stem separation import (the local Demucs service) + system-audio capture.
- **[src/audio-dsp/layers/](src/audio-dsp/layers/)** — LAYERS: a voice made of other voices. `layer-spec` (the rack, and the TWO ways a note picks a layer — by keyboard ZONE when a person plays, by an INDEX the note carries when something upstream already knows), `layers-renderer` (builds sub-renderers through the registry and sums them; no divide-by-N), `register` (side-effect import into the worklet bundle). The host half is [src/engines/layers-engine.ts](src/engines/layers-engine.ts) + `layers-rack-ui.ts`. It is the one in-tree engine that could not be a plugin: it reaches into the renderer registry to build OTHER engines, which the plugin ABI deliberately forbids. Three declared hooks carry it without an `engineId === …` anywhere in the core — `dynamicParamsFor` (a slot's engine contributes its knobs, prefixed `l0.`), `structuralFor` (the rack, which is not a number, posted on the worklet's `structural` channel) and `extraUI` (the rack's dropdowns). Changing what a slot HOLDS rebuilds the lane, because the worklet numbers a lane's params once for its lifetime; changing a zone or a gain does not.
- **A clip's LENGTH and its TEMPO are two different questions**, and `core/clip-time-scale.ts` owns both. `scaleClipTempo` (`*2` / `/2`) conflates them on purpose-by-accident: `*2` compresses AND tiles, `/2` stretches AND grows — which is why the same press feels right on drums and wrong on a pad. `applyClipLength` separates them, taking a `mode` (repeat / stretch / repeat-and-vary) and any factor. The note arithmetic is the pure `weave/clip-length.ts`; what lives in `clip-time-scale` is everything that must stay in step with it — bar count, loop region, automation curves. Building length controls on the pure function ALONE would be a second clip-time system, and the one that forgot the envelopes: a clip whose automation silently stops lining up with its notes.
- **The six WEAVE macros reach the sound three different ways**, and which way is a property of the macro, not an implementation detail. Density and Energy rewrite NOTES (they come down the weave's note source, so moving one only needs the cached source dropped). Space and Motion write PARAMS — through `app/weave-param-macros.ts`, which lands them on the destination catalogue via the PLAYBACK door, never the live-gesture one: a macro owns its value, so mirroring it into `engineState` would stamp a knob's momentary position into the lane's saved sound. Darkness and Style mix colour what the weave DRAWS and BLENDS — the scale its degrees walk, the shelf its loops come from — and are deliberately local to `weaveLoopContext` rather than written into `musicality`, because the toolbar's key and scale are the user's.
- **[src/weave/](src/weave/)** — WEAVE's pure core: the crossfade between loops that never stops moving. `metric-weight` (which positions hand over first), `blend-rhythm` (what two patterns SHARE never moves — that skeleton is what holds the bar up), `blend-melody` (pitches walk in scale DEGREES, so it cannot detune by construction), `blend-clip` (`blendLoops` — the one entry point: a list of `(loop, weight)` in, notes out), the three topologies (`topology-ab` / `-queue` / `-cloud`, all reducing to that same list, which is why all three ship for the price of three small files), `harmony-guard` (deliberately LESS than harmony: two forbidden intervals against the leading lane's lowest note), `macro-notes` / `macro-params` / `style-mix` (the six macros), `momentary` (hold-and-restore — the primitive the Roland MC research names as the one Loom lacked), `weave-state` + `weave-runtime` (the NOTES a lane plays instead of its clip's own, via `SchedulerContext.notes`. It was a per-note predicate first, and that shape could not work: a predicate over `clip.notes` can only take hits AWAY, so the far end of a crossfade came out silent instead of handed over to the other loop. Found by counting triggers through the real transport — `app/weave-scheduling.test.ts` — after every isolated test passed. A woven note may carry `layerIndex`, the loop it survived from, which a LAYERS lane reads as which of its instruments plays it). No DOM, no `AudioContext`, no module state.
- Also: `automation/` (the destination registry), `notefx/` (per-lane arp + chord + random note-FX, replaced the old global `arp/`), `demo/` (baked MIDI demos + picker), `patterns/`, `perf/` (PERF HUD), `styles/` (SCSS).

### Lane selection has ONE door

`SessionHost.focusLane(laneId, origin)` is the only thing that changes which lane is selected. Every entry point routes through it — lane header, clip cell, **mixer column background**, engine-swap re-route, APC Key 25 / MIDI (`loom-facade.setActiveLane`), the collapse chevron, and the undo/redo repaint. `showLaneEditor` is no longer an entry point: it is what `focusLane` calls to paint, alongside `renderWithMixer`. This exists because the clip editor and the instrument controls used to point at two different lanes at once — you edited lane A's notes while your knob turns landed on lane B.

Three things about it that are easy to break:

- **`origin` is load-bearing, not decoration.** Opening a clip already calls `focusLane`, and `focusLane` decides which clip to show. `'clip'` means "a clip was just opened — do not touch the clip editor"; `'lane'` means everything else. Without it, selecting a clip in lane B would open it and immediately close it. `clip-editor-lane-switch.test.ts` → *"opening a clip never closes the editor it just opened"* guards exactly that.
- **The clip follows the lane, and `null` means CLOSE — never create.** `clipToShowOnLaneSwitch` resolves a row (the open clip's row, else the launched scene's row, else none) and returns that row's clip on the new lane, or `null` if the slot is empty. The instrument page always follows the selected lane; the clip editor is the only thing that can end up showing nothing.
- **The two CLEARING writers are not selection.** `session-host-callbacks`'s `run` (selected lane deleted) and `session-host-persistence`'s `reconcileOpenEditors` (lane gone after a state swap) set `activeEditLane` to `null` and close both sides together. They are the teardown path and must not be routed through the funnel.
- **Finding every caller is a grep job, not a graph job.** GitNexus reports only ONE upstream caller of `focusLane`; the APC/MIDI one reaches `SessionHost` through a deps object and the call graph does not see it. This codebase is built almost entirely out of deps objects, so `impact --direction upstream` systematically under-reports these edges. Grep for `focusLane` / `showLaneEditor` across `src/` instead — trusting the graph here is the exact omission that produced the original bug.

`instrumentPageLaneId` (`LaneEngineHostState`) is written in exactly one place, and only when the selected lane routes to the **instrument** page — selecting a DRUM lane deliberately leaves it pointing at the last melodic lane. That is correct: the instrument page is not on screen for a drum lane, and pointing it there would blank the engine dropdown, mount the instrument FX panel under the drum lane's id, and aim the preset and engine-swap dropdowns at it.

## WEAVE — the panel is a PLUGIN, and four rules that cost a session to relearn

The crossfade-between-loops surface. Its pure core is `src/weave/` (above); what follows is the half that is easy to get wrong.

- **The panel is a plugin and has NO hot reload.** [plugins/weave/](plugins/weave/) compiles to `public/plugins/weave/main.js`, and Vite serves `public/` as static bytes. Every panel edit needs `npm run build:plugins` **and a full page reload** — the SCSS in `src/styles/` hot-reloads, the panel never does. "My change isn't showing" is this, almost every time.
- **`refresh()` REMOUNTS the panel.** [panel-views.ts](src/app/panel-views.ts) does `root.replaceChildren()` and mounts again, so calling it from a continuous control destroys the very element the pointer is holding: a click survives (one event) and a drag dies on the second. Refresh when a control APPEARS or DISAPPEARS, never while one is moving. This shipped twice as "the fader can't be dragged".
- **A weaving lane IGNORES its clip.** With loops chosen, [weave-wiring.ts](src/app/weave-wiring.ts)'s `build` reads the SELECTION and nothing else, so a scene launch decides only *whether* the lane plays, never *what*. Every scene sounds the same on that lane, a scene of empty clips included — and a scene written by PRINT plays the weave rather than the print. Known, reported, and not yet decided.
- **The fold chain's ORDER is load-bearing**, in `rawFor`: `build` → `withTimeScale` → `withProgression` → `withOctave` → the leader guard. Tempo first so the chords still walk the session's bars; the octave after the progression so it is not undone by it; both before the guard, which measures the lowest note that will actually SOUND. Being in the fold at all is what gets each of them into PRINT for free — `lapNotes` reads the same sources.

Three more things the core asks about a weaving lane:

- **Loop ids** are `clip:<id>`, `lib:<style>:<kind>:<index>` and `chord:<shape>` ([loop-ids.ts](src/weave/loop-ids.ts)). "The shelf" is **`!id.startsWith('clip:')`** — never `startsWith('lib:')`, which silently excludes generated chords and has broken three separate things (an empty shelf, pads that never evolved, a dead re-hook).
- **A lane's ROLE** — bass / comp / pad / arp / melody — is resolved by `laneRoleOf` ([lane-role.ts](src/session/lane-role.ts)): the user's mark wins, the engine's `defaultRole` is the fallback, a percussion lane has none. It decides which shelf the lane reads and in which register.
- **The SOUND control wears the shape of the lane's LOOP control** — a fader on A→B, a square on a cloud — and it is a rack of instruments underneath, balanced by `l0.gain`..`l3.gain`. Turning it on BUILDS that rack. Watch the gains: the rack's own `gain` field, the `l{i}.gain` params and `weave-sound.apply` can all write them, and a rebuild resets every param to its spec default (`l1.gain` defaults to **1**), which plays every instrument at once until something re-writes them.

## TB-303 behaviors that drive the design

These live in the TB-303 plugin ([plugins/tb303/dsp.ts](plugins/tb303/dsp.ts) + the lane scheduler) and shaped the slide/accent model now shared more broadly. The engine moved out of `src/` with the plugin cutover, but the *host* half of both behaviours stayed — which is why they are documented here and not in the plugin.

- **Slide** — there is **no slide flag on a note**: `NoteEvent` is `{ start, duration, midi, velocity }`. A note slides when the *previous* note is still holding over its start — `noteTrigger` ([lane-scheduler.ts](src/core/lane-scheduler.ts)) sets `slidingIn` when another note in the clip started earlier and still covers this note's start tick, and the renderer then ramps pitch and *skips the amp re-attack* so the previous gate keeps holding. That is why the bass generator writes overlapping durations (1.5× step) for the steps it wants to slide. **The scheduler does not know the id `tb303`**: it asks `slidesOnOverlap(engineId)` ([capabilities.ts](src/plugins/capabilities.ts)), which is true for an engine whose manifest declares `"slide": "overlap"`. Any plugin may opt in; an engine that says nothing never slides.
- **Accent** — not a flag of its own either: a note is accented when `velocity >= 100`. On the 303 it raises the filter-envelope peak, bumps Q, **shortens** the filter decay and adds an amp punch; on drums it scales the hit level; on Westcoast it drives the wavefolder only, not the amp. The 0..1 curve behind all of it has one owner, [src/core/velocity-gain.ts](src/core/velocity-gain.ts).

## When adding/changing things

- **Add an engine, an insert or a modulator — write a PLUGIN, do not touch `src/`.** This is the default and it is what the six melodic engines, the fifteen inserts and S&H all do. See [docs/plugin-development.md](docs/plugin-development.md) for the full walkthrough; the shape:
  1. `npm run plugin -- new plugins/<id>` scaffolds the directory.
  2. `plugin.json` declares everything the host reads: `id`, `loomApi: 1`, one or more `components`, each with its `kind` (`engine` | `fx` | `modulator`), `params`, `groups` (which sections exist, their title, order, colour, and which share a row — omit it and the grid falls back to first-appearance order, one row per group, no colour), an optional `modulators` array shipped with the sound, and a `capabilities` block. Optional `presets: "presets.json"` and `dsp: "dsp.js"`.
  3. `dsp.ts` for anything that synthesises — the per-sample renderer, registered via `Loom.registerRenderer` INSIDE the worklet. `main.ts` for an insert, which builds native Web Audio nodes on the main thread. An insert is NOT a worklet: only synthesis runs there.
  4. **Implement the live-params hook** — a knob must move the note ALREADY sounding, not just the next trigger. Read your CONTINUOUS params from the live bag every sample; copy STRUCTURAL params (waveform, filter model, unison size, envelope TIMES) to your own fields once, at construction, from the trigger-time snapshot. The hook is optional, so a renderer that skips it compiles clean and passes the whole suite — it is just the one engine whose knobs go dead mid-note. `audio-dsp/live-params.dsp.test.ts` walks the registry and catches it.
  5. `npm run build:plugins`. **Nothing you did is visible until this runs** — the app loads `public/plugins/`, not `plugins/`.
  There is no `WORKLET_ENGINE_IDS` list to edit any more: it is a live view over "is this id worklet-hosted", and any plugin id answers yes.
- **Adding an engine in-tree is the EXCEPTION, and needs a reason.** The three that live in `src/engines/` are there because they own browser resources a plugin cannot hold — decoded buffers, IndexedDB, per-voice `AudioParam`s. "I have a checkout so it's easier" is not that reason; an in-tree engine is a file every future PR review has to carry.
- **Never add an `engineId === '…'` to the core.** Add the question to [src/plugins/capabilities.ts](src/plugins/capabilities.ts) as a named accessor with a safe default, and let each component answer from code or from its manifest. Every accessor there defaults to "behaves like an ordinary melodic instrument" on an unknown id, and NEVER returns undefined — an unregistered engine that blanked its lane's UI would fail silently.
- **Add a drum kit** — a SYNTH kit is an object appended to the `KITS` array in [src/core/drums.ts](src/core/drums.ts) (parameter bags over the same DSP primitives); a SAMPLE kit is an entry in `public/presets/drum-kits.json`, loaded by `presets/drum-kits-loader.ts`. Add a new drum *voice* by extending the `DrumVoice` union + `DRUM_LANES` + its params interface + every kit + `seedSynthState`, then the matching renderer in [src/audio-dsp/drums/voices.ts](src/audio-dsp/drums/voices.ts) and a MIDI number in [src/engines/drum-gm-map.ts](src/engines/drum-gm-map.ts).
- **Add a preset** — for a melodic engine, add an entry to that plugin's own `plugins/<id>/presets.json` and rebuild the plugin; for Sampler or Drums, to `public/presets/<engine>.json`. Either way JSON is the source of truth, and the `gm` program tag is optional.
- **Add a bundled sampler INSTRUMENT** (a multisample fetched by id, not a preset carrying its zones inline) — write `public/instruments/<id>.json` with `family: 'melodic'` or `'loop'`, drop its audio in `public/instruments/<id>/`, and add a line to `public/instruments/index.json`. **The index is the whole discovery mechanism**: the dropdown builds one group per family off it, and an instrument missing from it is loadable by a saved session and unpickable by hand — which is exactly how fourteen of them shipped invisible.
- **Anything that writes an engine param from the UI** MUST go through `commitParam` (or `commitParamForLane` when you hold the session directly) in [src/engines/engine-param-commit.ts](src/engines/engine-param-commit.ts) — never `engine.setBaseValue` alone. The mirror into `lane.engineState.params` is the ONLY vehicle by which a knob value reaches a save; four builders that skipped it threw the user's edit away silently.
- **File size** — measured in LINES OF CODE: comment and blank lines do **not** count. Target 300, hard cap 500. Quote the code-line figure when you claim a file is under the cap (`src/main.ts` is 473 code lines in 816 physical ones).
- **Scheduling** — `bpm`/`length` are mutable at runtime; the next scheduled step uses the new values. Step duration is `60 / bpm / 4` (16th notes). The visual playhead is a separate timer matched to the scheduled audio time and may drift under tab throttling, but audio scheduling is unaffected.
- **Session UI** — the clip grid and inspector are rebuilt by `session-host`; clip cells cycle/launch and the inspector auto-renders the engine editor. Don't hand-roll a parallel render path — go through `session-host`.
- **Anything that lists parameters the user can target** (a modulation dropdown, an automation picker, an XY pad axis, a MIDI mapping) MUST call `DestinationRegistry.list()` from [src/automation/destination-registry.ts](src/automation/destination-registry.ts) and `subscribe()` to stay fresh. Do NOT enumerate the knob registry and do NOT build a parallel list — that is how four inconsistent pickers happened. See [docs/automation-destinations.md](docs/automation-destinations.md).

## Approved mockups & honest "done" (process — learned the hard way 2026-06-06)

A failed Sampler overhaul (shipped the OLD UI instead of the approved mockup; a loop preset that never played) traced to one root cause: **the approved mockup was never turned into verifiable requirements**, and "tests green" was treated as "done". Rules:

- **An approved mockup is a committed artifact.** When the user approves a mockup, save it in-tree next to its spec (`docs/superpowers/specs/<date>-<topic>-mockup.html`) and link it from the spec. NEVER leave it as a throwaway `public/*-mockup.html` — those get deleted (the Sampler one was lost, uncommitted, forever).
- **The spec must link the mockup and name what it drops.** If a spec defers or excludes any part of the approved *look*, that is the **user's** call → a `⛔ CONFIRMAR` block, not a silent scope cut. Re-scoping "make it like the mockup" into "reorganise the logic on the old UI" is the exact failure to avoid.
- **Visual parity is an acceptance criterion.** For any work with an approved mockup, "done" requires a human look: load the real screen, screenshot, compare side-by-side with the mockup. Automated tests do not check whether it matches what was approved.
- **One test per user path.** No `(or …)` alternatives in test tasks — they let a broken path (e.g. the loop *preset* picker) hide behind a working one (loop *import*). Each path gets its own test.
- **Don't claim a UI feature "done"/"verified" without opening it and looking.** (Complements "lean on code, not the browser" for *debugging* — but for *done-claims on UI*, the browser look is mandatory.)

## Driving Loom in Playwright — load a MIDI + play a scene (exact flow; don't rediscover it)

A real session burned ~20 turns fumbling this. Follow it verbatim.

- **Server:** the build under test is whatever `npm run dev` serves at <http://localhost:5173> (a worktree has its own — run `npm run dev` inside the worktree). The Playwright MCP server's cwd is the **MAIN checkout**: default `browser_snapshot` files land in `<repo-root>/.playwright-mcp/`, but a snapshot taken with a custom `filename` lands in `<repo-root>/` itself — `Glob`/`Grep` to find it.
- **Snapshots are huge** (every lane has an engine/preset dropdown → 2000+ lines, exceeds the token cap). NEVER read a full `browser_snapshot`; save to a file + `Grep` for the ref you need, or query the DOM with `browser_evaluate`. Toolbar refs (`#play` ▶, `#stop` ⏹, the menu-bar `File`/`Tools` triggers) are stable across reloads; grid refs are not.
- **Import a MIDI (two steps — the file picker is NOT the commit):**
  1. Menu bar **File → "Import MIDI…"** → opens `<dialog id="midi-import-dialog">`. Click its file input `#midi-import-file` → file-chooser modal → `browser_file_upload` with the absolute `.mid` path.
  2. The dialog then shows a per-track preview and enables **"Import MIDI"** (`#midi-import-load`). Click it → a SECOND modal (`<dialog id="app-dialog">`) whose action buttons are **Cancel / Replace / Add**. Click **Replace** (or Add) — THAT is the commit. Both dialogs are modal and intercept pointer events, so nothing else (incl. ▶) is clickable until you resolve them.
- **Play a SCENE — ALWAYS use the scene launch, not the global transport (user's standing preference):**
  1. Click the **"Session"** view tab.
  2. A scene is a ROW of per-lane clip cells. That row has ~N **per-clip ▶** buttons (one per lane) — do NOT click those, each launches a single clip. The **scene launch** is the row's own **named button `▶ <SceneName>`** at the end of the row (a MIDI import creates a scene named **"MIDI Import"** → click **`▶ MIDI Import`**). That launches ALL clips in the scene = the whole arrangement. (Clicking a clip ▶ instead of the named scene button is the exact mistake that cost ~20 turns, twice.)
- **Audio gating:** only a TRUSTED click (`browser_click`) resumes the AudioContext + counts as the play gesture. A synthetic `.click()` via `browser_evaluate` does NOT — it's fine for dismissing the import dialog (Replace), NOT for the scene/transport play.
- **Objective audio measurement (master tap):** no `window.__loom`/audio global exists, so to measure peak/RMS/cortes: `browser_run_code_unsafe` → `page.addInitScript(...)` BEFORE boot, then reload. The init script wraps `window.AudioContext` so each instance does `createAnalyser()`, pre-connects it to `ctx.destination`, and monkeypatches `AudioNode.prototype.connect` to route anything connecting to `destination` THROUGH the analyser; stash analyser→`window.__an`, ctx→`window.__ctx`, and run a rAF max-peak tracker into `window.__peak`. Then per frame `getFloatTimeDomainData` → RMS+peak; **near-silent frames mid-playback = cortes; peak ≥ 1.0 = clipping.** VERIFIED 2026-06-24: dense 16-channel "Children" through the worklet scene = **peak 0.92 (no clip), RMS ~0.23 steady, 0 near-silent frames (no cortes)**.

## Dense-MIDI "cortes"/dropouts — already diagnosed, do NOT re-investigate

Dropouts under dense polyphony were the **node-per-note architectural ceiling** (per-note Web Audio node churn → GC starves the main-thread scheduler), diagnosed at length (memory `project_voice_lifecycle_graph_leak`). **The cure — the AudioWorklet engine rewrite — SHIPPED and is merged on `main`**: the worklet is now the sole synthesis path and the legacy node-per-note layer is deleted. Dense "Children" MIDI runs clean where node-per-note couldn't. If dropouts resurface, they are a NEW bug — don't re-derive the old diagnosis, and don't look for a "worklet build" to compare against.

> **Voice cap REMOVED (commit `96b8fea`):** the spec's "global polyphony cap" was reversed — a finite per-lane cap evicted still-sounding voices (`VoiceManager.spawn` did `slots.shift()` before the voice's release rendered → a step discontinuity → audible **clicks** in dense parts). Now: poly lanes are UNCAPPED, mono lanes (`maxVoices === 1`) still steal their previous voice, global cap = `Infinity`. **Do NOT re-add a finite voice cap — it clicks.** (Details in memory `project_audioworklet_engine_rewrite`.)
